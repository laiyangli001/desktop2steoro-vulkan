# Python软件授权保护系统 —— 完整实现计划书


## 一、项目概述

### 1.1 项目背景

本软件是一款**离线运行、一次性买断**的Python桌面应用，面向全球用户（含中国大陆及海外市场）。核心需求包括：

- **防AI/防破解**：保护启动流程，防止授权被绕过
- **灵活的离线使用**：用户可选择免验证天数，期间无需联网
- **防账号共享**：同一账号同时只能一台设备在线
- **低成本服务器架构**：日活数万用户，服务器负担最小化
- **全球化付费系统**：支持多币种、多支付方式

### 1.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **安全在签名，不在混淆** | Python代码保持明文，核心验证逻辑依赖密码学签名 |
| **数据依赖而非流程分支** | 验证失败时“隐式毒化”数据，而非显式报错 |
| **离线可用但有期限** | 支持离线运行，但必须有到期机制防止永久滥用 |
| **服务器无状态** | 尽量少存用户状态，降低数据库压力和运维成本 |


## 二、防AI破解与核心安全架构

### 2.1 整体架构：三层防御

```
┌─────────────────────────────────────────────────────────────┐
│                    第1层：C扩展层（核心堡垒）               │
│  • 用Cython/C++编译为.pyd/.so                             │
│  • 内置RSA公钥，执行签名验签                               │
│  • 采集设备指纹（HWID）                                    │
│  • 执行时钟防篡改检测                                      │
│  • 验证失败时返回“毒化数据”而非异常                        │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                    第2层：Python授权层                      │
│  • 调用C扩展获取解密密钥/签名                              │
│  • 管理本地令牌存储                                        │
│  • 执行天数策略和撤销逻辑                                  │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                    第3层：业务逻辑层                       │
│  • 使用C扩展提供的密钥解密配置、生成API签名                │
│  • 无显式授权检查——拿不到正确密钥则功能异常                │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 核心机制：签名令牌（Signed Token）

**首次激活流程**：

1. 用户输入账号密码，客户端采集设备指纹（HWID）
2. 客户端向服务器发起激活请求，携带HWID
3. 服务器验证账号密码后，用**RSA私钥**签发JWT令牌，载荷包含：
   - `hwid`：设备指纹
   - `user_id`：用户ID
   - `issued_at`：签发时间
   - `expire_at`：免验证截止日期
   - `mode`：授权模式（天数模式/永久绑定/在线模式）
4. 服务器将令牌返回客户端，客户端加密存储于本地

**离线验证流程**：

1. 客户端启动时读取本地令牌
2. 调用C扩展验签（用内置公钥）——确保令牌未被篡改
3. 解析令牌中的HWID，与当前设备指纹比对
4. 检查当前时间是否超过`expire_at`
5. 全部通过 → C扩展返回**真实的解密密钥**；失败 → 返回**毒化密钥**（见下文）

### 2.3 防AI破解的“隐式毒化”策略

传统做法是验证失败时`raise Exception`或`exit()`，AI可以轻松定位并绕过。

**本方案采用“数据毒化”**：

| 验证结果 | C扩展行为 | 软件表现 |
|---------|----------|---------|
| ✅ 通过 | 返回正确的AES解密密钥 | 配置解密正常，功能完整 |
| ❌ 失败 | 返回一个“看似正常但错误”的密钥 | 程序正常运行、不报错，但所有数据解密后为乱码 |

**效果**：AI拿不到任何异常堆栈，程序“正常”运行但输出全错。AI无法根据报错定位授权检查点，除非完整理解整个业务算法。

### 2.4 防时钟篡改

为防止用户通过修改系统时间延长离线有效期，C扩展实现**高水位标记（High-Water Mark）**机制：

- 每次成功验证时，在本地加密存储当前网络时间戳
- 每次启动时对比：`当前系统时间 < 上次记录时间` → 判定为时钟回拨 → 授权失效
- 利用系统运行时长（`/proc/uptime`）辅助校验，增加伪造难度

### 2.5 技术选型建议

| 组件 | 推荐方案 | 说明 |
|------|---------|------|
| C扩展编译 | **Cython** | 将Python核心逻辑编译为`.pyd`/`.so`，提高逆向难度 |
| 签名算法 | **RSA-2048 或 Ed25519** | 私钥存服务器，公钥内置C扩展 |
| 令牌格式 | **JWT** | 标准化，易于解析和验签 |
| 设备指纹 | SHA-256(MAC+CPU+主板序列号) | 全平台统一 |
| 本地加密存储 | AES-GCM + 动态Nonce | 防止令牌被直接读取篡改 |


## 三、离线天数选择与账号管理机制

### 3.1 三种授权模式

用户首次登录时，可选择以下三种模式：

| 模式 | 说明 | 换设备规则 | 适用场景 |
|------|------|-----------|---------|
| **A. 天数免验证** | 选择1-30天免联网验证 | 30天冷却期内可免费撤销1次 | 大多数用户（默认推荐） |
| **B. 永久绑定** | 永久离线，永不联网验证 | **不可换设备**（需客服介入） | 长期固定设备的用户 |
| **C. 在线模式** | 每次启动联网验证 | 可任意换设备 | 多设备切换用户 |

### 3.2 天数免验证模式（核心模式）

**规则设计**（消除“窗口期轮换”漏洞）：

| 规则 | 数值 | 说明 |
|------|------|------|
| 免验证天数上限 | **30天** | 用户可选1-30天 |
| 免费撤销冷却期 | **30天** | 从上一次撤销成功之日起算 |
| 付费撤销 | $2.99/次 | 每月限购2次（阶梯定价） |
| 免验证延长包 | $2.99/+30天 | 在现有期限上叠加，不重置冷却期 |

**核心原则**：`免验证天数（30天） ≤ 撤销冷却期（30天）`，彻底封堵“在免验证窗口内多次撤销换设备”的漏洞。

**用户操作流程**：

```
用户选择「30天免验证」
    ↓
服务器签发令牌，expire_at = now + 30天
服务器记录：该账号锁定设备A，锁定截止日期 = now + 30天
    ↓
30天内：设备A可完全离线运行
    ↓
【场景1：30天内想换设备】
    点击「撤销解绑」（消耗免费撤销额度，30天冷却期开始）
    → 服务器解绑设备A
    → 设备B登录，重新选择天数
    ↓
【场景2：30天后自动到期】
    软件提示“免验证已到期，请联网续期”
    → 联网后自动续期（可重新选择天数）
```

### 3.3 付费撤销机制（防滥用+创收）

**定价策略**：

| 当月购买次数 | 单价 | 说明 |
|-------------|------|------|
| 第1-2次 | $2.99 / ¥19.9 | 正常用户偶尔换机 |
| 第3-5次 | $4.99 / ¥34.9 | 频繁换机者，成本上升 |
| 第6次以上 | $9.99 / ¥69.9 | 恶意行为，成本极高 |

**每月限购5次**，超出后提示“操作过于频繁，请下月再试”。

**效果**：正常用户每年买1-2次完全可接受；恶意共享者若频繁撤销，成本快速超过买新软件。

### 3.4 永久绑定模式

**强警告流程**：

> ⚠️ **永久绑定警告**
>
> 选择此模式后，该账号将**永久锁定**在当前设备，**永不支持换机**。
>
> 此操作**不可逆**，请确认您的设备不会更换。
>
> 请输入 `我已知晓并承担后果` 以确认。

**例外通道**：每个账号一生可申请1次“人工解绑”，需提供购买凭证，由后台人工审核处理。

### 3.5 在线模式

- 每次启动联网验证
- 服务器不锁设备，可任意换设备登录
- 客户端本地缓存验证结果1小时，减少服务器请求

| 项目 | 说明 |

⚠️ **风险提示**：开源方案需要自己申请和维护支付通道，部分“免签约”方案处于政策灰色地带，建议优先考虑支付FM这类有正规资质的平台。

| **提现** | ✅ **最大亮点：支持直接提现到支付宝**，对中国开发者非常友好 |
| **注意** | 产品较年轻，建议配合其他渠道分散风险 |

| 项目 | 说明 |

## 五、支付与授权联动架构

```
                          ┌────────────────────────────────┐
                          │         你的授权服务器         │
                          └───────────────┬────────────────┘
                                          │
                  ┌───────────────────────┼───────────────────────┐
                  ↓                       ↓                       ↓
         ┌────────────────┐     ┌────────────────┐     ┌────────────────┐
         │  国内支付通道   │     │  国际支付通道   │     │  回调验证网关   │
         │  (支付FM)      │     │  (Creem)      │     │  (统一入口)    │
         └────────────────┘     └────────────────┘     └────────────────┘
                  ↓                       ↓                       ↓
         用户扫码/付款          用户信用卡/PayPal         Webhook签名验证
                  ↓                       ↓                       ↓
         支付成功回调            支付成功回调              验证通过后授权激活
```

**关键安全设计**：

| 安全措施 | 说明 |
|----------|------|
| **Webhook签名验证** | 两套系统都必须验证回调来源的签名，防止伪造支付通知 |
| **订单号唯一性** | 每笔订单生成唯一ID，防止重复激活 |
| **用户关联** | 支付回调携带 `user_id`，支付成功自动关联到该用户账号 |
| **试用心跳** | 支付成功后，服务器立即更新用户状态为“已付费”，并下发正式令牌 |


## 六、一个月免费试用 + 付费转化流程

```
用户注册账号
    ↓
自动获得30天免费试用
  （服务器记录 trial_expire_at = now + 30天）
    ↓
试用期内：完整功能，联网验证时状态为“试用中”
    ↓
到期前3天：弹出提示“您的试用期即将结束”
    ↓
到期后：软件锁定，弹出付费引导页面
    ↓
用户选择支付方式（国内/国际）
    ↓
支付成功 → 服务器标记为“已付费” → 下发正式授权令牌
    ↓
永久使用（或按模式A/B/C的规则）
```

**技术实现要点**：

- 服务器记录 `trial_expire_at` 字段
- 客户端每次验证时，服务器返回 `trial_expire_at`，客户端本地校验
- 到期后客户端弹窗引导付费，并可一键跳转到支付页面（调用对应支付系统）
- 试用期不限制功能——因为你的目标是“让用户充分体验，满意再付” 💪

```
支付成功 → 支付平台发送Webhook到你的服务器
    ↓
服务器验证Webhook签名，确认支付有效
    ↓
服务器将该用户账号标记为“已付费”，生成授权令牌
    ↓
客户端下次联网验证时获取正式授权
```

**关键设计**：支持**一个月免费试用**，试用期内功能完整，到期后需要付费才能继续使用。试用期通过服务器下发的`trial_expire_at`字段控制。

### 4.4 付费撤销的收入处理

付费撤销（$2.99/次）通过Stripe一次性支付通道处理，与主软件购买共用同一支付系统。建议在产品官网单独设立“增值服务”页面，供用户购买撤销次数和延长包。

### 5.4 服务器性能评估

**请求量估算**（5万日活用户）：

| 场景 | 日均请求 | 峰值QPS | 说明 |
|------|---------|---------|------|
| 首次激活 | ~500 | <1 | 每人仅首次 |
| 日常验证（天数模式） | ~1,600 | ~2 | 30天验证一次 |
| 日常验证（在线模式） | ~10,000 | ~10 | 每天启动一次 |
| 撤销操作 | ~100 | <1 | 低频操作 |
| **总计** | **~12,000** | **<15** | |

**结论**：单台普通服务器（2核4GB）+ Redis，可轻松支撑5万日活。

### 5.5 防滥用机制

| 机制 | 实现方式 |
|------|---------|
| **频率限制** | Redis计数器，每用户每分钟限N次 |
| **异常检测** | 同一IP大量激活 → 临时封禁 |
| **Webhook签名验证** | 支付回调必须验证Stripe签名，防止伪造 |
| **令牌签名** | JWT由服务器私钥签发，客户端公钥验签 |

### 6.2 C扩展接口设计（伪代码）

```cpp
// license_core.cpp (Cython/pybind11)
class LicenseCore {
public:
    // 初始化授权，返回AES密钥（验证失败返回毒化密钥）
    std::string init_license(const std::string& token,
                              const std::string& hwid);

    // 解密数据（使用init_license返回的密钥）
    std::string decrypt_data(const std::string& encrypted_data);

    // 生成API签名（验证失败返回空）
    std::string sign_request(const std::string& data);

    // 获取当前授权状态（供UI显示）
    LicenseStatus get_status();

    // 时钟防篡改检查
    bool check_clock_integrity();
};
```

### 6.3 Python调用示例

```python
import license_core
import json

# 启动时初始化
token = load_local_token()  # 从本地加密存储读取
hwid = get_device_fingerprint()
aes_key = license_core.init_license(token, hwid)

# 解密配置文件（如果aes_key是毒化的，解密结果就是乱码）
config_encrypted = open("config.enc", "rb").read()
config_json = license_core.decrypt_data(config_encrypted)
config = json.loads(config_json)  # 毒化密钥会导致json解析失败

# 业务逻辑正常运行，但拿不到正确配置
run_business(config)  # 传入的是错误数据
```

**关键点**：Python代码中没有任何`if authorized:`的判断。AI无法通过搜索关键词定位授权检查点，整个程序的正常运行天然依赖C扩展提供的正确密钥。

## 八、风险与应对

| 风险 | 应对措施 |
|------|---------|
| **C扩展被逆向** | 定期更新毒化逻辑；核心算法仍在服务器端 |
| **AI辅助破解** | “隐式毒化”无报错，AI无法定位；配合C扩展二进制难以分析 |
| **账号密码泄露** | 设备指纹绑定，换设备需重新激活，旧设备到期失效 |
| **支付欺诈** | Stripe风控 + Webhook签名验证 |
| **服务器宕机** | 已激活用户可离线运行至到期；监控+自动恢复 |
| **法律风险** | 用户协议明确禁止逆向工程和账号共享 |


## 九、总结

本方案的核心设计理念可以概括为：

> **“防君子也防小人，让破解的成本远高于购买的成本。”**

通过 **“C扩展 + 签名令牌 + 隐式毒化”** 的三层防护，即使AI能看懂全部Python代码，也无法绕过编译后的C扩展中的核心验证逻辑。通过 **“30天免验证 + 30天撤销冷却期”** 的对齐设计，彻底封堵了账号共享的“窗口期轮换”漏洞。通过 **“轻量级服务器 + Redis缓存”** 的架构，5万日活用户的服务器成本控制在极低水平。通过 **“¥99 / $29.9定价 + 一个月免费试用”** 的策略，在用户接受度和商业可持续性之间取得平衡。

**这不是一个“绝对防住”的方案，而是一个“让破解变得极其不划算”的方案。** 在AI时代，这才是软件保护的现实最优解。
