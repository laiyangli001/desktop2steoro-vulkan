# NVIDIA NvFRUC 全模式补帧实现计划书

## 1. 文档目的

本文档定义 Desktop2Stereo 在 Windows NVIDIA 平台上，将现有依赖外部 Lossless Scaling 窗口捕获的“LSFG/小黄鸭”选项替换为进程内 NVIDIA NvFRUC 2× 帧生成的实施方案。

本方案首期覆盖以下运行模式：

1. 本地查看（Local Viewer）
2. 3D 显示器（3D Monitor）
3. OpenXR
4. MJPEG 推流
5. 高级网络推流

本方案不修改现有规格文档，也不涉及 macOS 原生链路。

## 2. 实施目标

- 使用进程内 NvFRUC 完成立体帧生成，不依赖 Lossless Scaling 程序。
- 不创建、显示或捕获额外的补帧窗口。
- 分别处理左眼和右眼，保持双眼时间同步及单眼有效分辨率。
- 支持当前已有的 Half-SBS、Full-SBS 和 TAB 打包格式。
- 从立体推理结果到最终显示或编码均保持 GPU 资源路径，不增加 CPU 回读。
- 统一作用于所有运行模式，避免为本地显示、OpenXR 和网络推流分别实现补帧逻辑。
- GUI 中的目标帧率统一表示最终输出帧率，而不是补帧前的基础推理帧率。

## 3. 范围与约束

### 3.1 首期支持范围

- 操作系统：Windows。
- GPU 最低兼容型号：NVIDIA GeForce GTX 1650 SUPER（TU116）或更高型号，并且必须具备 NVOFA 硬件支持。
- 明确不支持：采用 TU117 芯片的 GeForce GTX 1630 和普通 GTX 1650。
- 推荐型号：GeForce RTX 2060 或更高型号；最低兼容型号仅代表能够调用 NvFRUC，不代表能够满足高分辨率双眼推理和补帧的性能要求。
- 帧生成倍率：固定 2×。
- 输入资源：CUDA 可访问的左右眼图像。
- 生效时机：开始运行时读取配置，不支持运行过程中热切换。

### 3.2 暂不包含

- Linux NvFRUC 集成。
- AMD、Intel 或其他 GPU 的帧生成实现。
- 2× 以外的帧生成倍率。
- 外部 Lossless Scaling 兼容回退。
- macOS CoreML、MPSGraph 或 Metal 链路。
- 对已经打包完成的整张 SBS 图像直接进行光流插帧。

## 4. 当前实现问题

当前 GUI 中的“小黄鸭/LSFG”选项只在高级网络推流模式显示。旧逻辑依赖查找可见的 `Stereo Viewer` 窗口，再让外部 Lossless Scaling 捕获该窗口或所在显示器区域。

该方案存在以下限制：

- 依赖外部程序和可见窗口。
- 只针对原 RTMP 窗口捕获链路，不能自然覆盖 OpenXR、本地查看及其他直接 GPU 输出。
- 当前主要运行链路已经使用直接 SBS 输出消费者，旧 RTMP 窗口捕获模块不再是统一输出入口。
- 无法把项目中的 CUDA/Vulkan 纹理直接交给 LSFG。
- 窗口位置、显示器映射和 DWM/独占全屏行为都会影响捕获稳定性。

因此，新实现不应继续扩展旧窗口捕获逻辑，而应在立体推理结果与各模式输出消费者之间增加统一的进程内帧生成阶段。

## 5. GUI 与配置设计

### 5.1 GUI 选项

将现有“小黄鸭/LSFG”选项改为勾选项：

> NvFRUC 补帧

布局规则：

- 将“运行模式”下拉框与“NvFRUC 补帧”勾选项放在同一行。
- 勾选项紧邻运行模式下拉框右侧并保持垂直居中，不另占一行。
- 勾选项隐藏时不保留空白占位，不改变运行模式下拉框原有宽度。

显示规则：

- Windows NVIDIA 环境下，在所有运行模式中显示。
- 非 NVIDIA 环境隐藏或禁用。
- 能识别为 NVIDIA、但运行时能力探测不通过时，选项保持不可用并显示具体原因。

Tooltip 应明确说明：

- 最低兼容型号为 NVIDIA GeForce GTX 1650 SUPER（TU116），并且必须通过 NVOFA/NvFRUC 运行时能力探测。
- 采用 TU117 芯片的 GTX 1630 和普通 GTX 1650 不受支持。
- 为满足深度推理和高分辨率双眼补帧性能，推荐使用 RTX 2060 或更高型号。
- 采用进程内 NvFRUC，不需要安装或启动 Lossless Scaling。
- 不会创建单独的补帧窗口。
- 设置 60 FPS 时，基础捕获、深度推理和立体生成目标约为 30 FPS，NvFRUC 输出至 60 FPS。
- 首次启用或运行环境发生变化时会自动检测当前完整链路能够稳定达到的最高补帧帧率，并预留 20% 性能余量。
- 用户选择的帧率超过安全上限时，程序会自动限制到检测值并在 GUI 和日志中说明请求值与实际值。
- 为保证正确的时间顺序，需要等待下一张真实帧，因此会增加约一个基础帧间隔的延迟。
- 该选项在下一次点击运行时生效，运行过程中不能热切换。

### 5.2 配置迁移

新增规范化配置项：

```yaml
NVIDIA Frame Generation: false
```

迁移规则：

1. 优先读取 `NVIDIA Frame Generation`。
2. 新配置不存在时，读取旧的 `Lossless Scaling Support` 作为兼容值。
3. GUI 下次保存设置时写入新配置项。
4. 运行时不再根据 RTMP 模式限制该值。
5. 旧配置只用于迁移，不再控制外部 Lossless Scaling 捕获。

## 6. NvFRUC 原生桥接

### 6.1 桥接职责

增加版本化 C ABI 桥接层，对 Python 隐藏 NvFRUC SDK 的结构体和资源生命周期细节。桥接层至少提供：

- 运行库及驱动能力探测。
- 上下文创建和销毁。
- CUDA 输入、输出资源注册与注销。
- 中间帧生成。
- 历史状态重置。
- 错误码和可读错误信息查询。

桥接库由项目构建，`NvFRUC.dll` 按 NVIDIA SDK 的可分发条款进入 Windows NVIDIA 运行包，并在安装或启动探测时检查版本和完整性。

### 6.2 双眼处理

为左眼和右眼分别创建 NvFRUC 上下文，并使用完全相同的输入时间戳和目标中间时间戳。

不得直接对整张 SBS 进行 NvFRUC 处理，原因包括：

- SBS 中央边界会干扰光流分析。
- 左右眼代表不同视点，不能被视为一张连续图像。
- Half-SBS 已经压缩单眼宽度，直接补帧不利于 OpenXR 保持单眼质量。
- OpenXR 消费的是左右眼资源，而不是最终打包图像。

生成左右眼后，调用现有打包逻辑重新生成当前输出格式的 Half-SBS、Full-SBS 或 TAB。

### 6.3 GPU 资源要求

- 输入和输出必须保持在 CUDA 设备内存。
- 不允许为了 NvFRUC 转换为 NumPy、PIL 或普通 CPU 缓冲区。
- 需要的颜色格式转换通过 CUDA 内核或现有 GPU 转换路径完成。
- 生成帧不得复用只属于真实帧的延迟 Vulkan 请求或最终 D3D11 合成表面。
- 启用帧生成时，应确保立体运行时保留可供 NvFRUC 使用的 CUDA 左右眼结果。

## 7. 帧率语义

### 7.1 两级帧率

将当前单一目标帧率拆分为：

- `output_target_fps`：GUI 设置的最终显示或推流帧率。
- `base_runtime_fps`：捕获、深度推理和立体生成目标帧率。

启用 NvFRUC 时：

```text
base_runtime_fps = ceil(output_target_fps / 2)
```

未启用时：

```text
base_runtime_fps = output_target_fps
```

例如：

| 最终目标帧率 | 基础目标帧率 | NvFRUC 理论输出 |
|---:|---:|---:|
| 30 | 15 | 30 |
| 45 | 23 | 46，最终按 45 FPS 节流 |
| 60 | 30 | 60 |
| 90 | 45 | 90 |

捕获和推理调度使用基础帧率；本地呈现、OpenXR 提交和网络编码器使用最终输出帧率。

### 7.2 延迟特性

为了输出正确的时间顺序，中间帧必须同时依赖前后两张真实帧。稳定阶段的输出顺序为：

```text
真实帧 A
→ A/B 中间生成帧
→ 真实帧 B
```

真实帧 A 需要等待真实帧 B 到达后才能组成完整输出组，因此会增加约一个基础帧间隔的等待延迟。该延迟是基于后向参考的帧生成所必需的，不能在不预测未来画面的情况下完全消除。

## 8. 统一运行管线

### 8.1 队列结构

现有运行时队列容量为 1，生产者和消费者都倾向于覆盖旧帧或清空队列后只取最新帧。该策略适合低延迟真实帧显示，但会直接丢掉插入的中间帧。

启用 NvFRUC 后改为：

```text
捕获
→ 深度推理与立体生成
→ 基础真实帧队列
→ NvFRUC 双眼帧生成阶段
→ 最终呈现队列
→ 当前模式输出消费者
```

要求：

- 基础队列继续允许丢弃过时的尚未处理真实帧，以限制推理积压。
- 最终呈现队列按 FIFO 消费。
- 输出消费者不得清空最终呈现队列后只取最新帧。
- 队列项应包含帧类型、源帧组编号、捕获时间戳、目标呈现时间戳和资源释放信息。
- 输出落后时按完整帧组丢弃，不能只丢中间帧或只丢真实帧。
- 停止程序时必须释放队列中尚未提交的 CUDA/NvFRUC 资源。

### 8.2 帧生成阶段

新增统一的 `NvFrucFrameGenerationStage`，职责包括：

1. 读取基础真实立体帧。
2. 等待并保存连续两张分辨率、格式和 CUDA 设备一致的真实帧。
3. 使用相同时间戳分别生成左右眼中间帧。
4. 重新打包生成帧的 SBS/TAB。
5. 按目标呈现时间将真实帧和生成帧写入最终呈现队列。
6. 记录真实帧、生成帧、跳过帧、失败帧和耗时统计。
7. 检测分辨率、格式、设备或上下文变化并重建资源。

### 8.3 各模式接入

- OpenXR：消费补帧后的独立左右眼资源。
- 本地查看：消费补帧后重新打包的 SBS/TAB。
- 3D 显示器：与本地查看共用最终呈现队列和补帧结果。
- MJPEG：消费补帧后的打包图像；仅在现有编码链必须使用 CPU 时发生原有转换，NvFRUC 阶段本身不得新增 CPU 回读。
- 高级网络推流：将补帧后的 SBS 直接交给现有 GPU 编码或兼容编码后端。

关闭 NvFRUC 时，继续使用当前低延迟“只取最新帧”行为，避免无谓增加排队延迟。

## 9. 能力探测与故障处理

### 9.1 启动前探测

用户勾选帧生成后，在启动处理子进程前验证：

- 操作系统为 Windows。
- 当前推理设备为 NVIDIA CUDA。
- GPU 至少为 GeForce GTX 1650 SUPER（TU116）或其他具备 NVOFA 的更高型号，并排除 TU117。
- NVOFA/NvFRUC 运行时能力探测成功；不能只根据显卡商品名称或“Turing”架构字符串判断。
- NVIDIA 驱动满足运行库要求。
- NvFRUC 运行库及项目桥接库可以加载。
- 左右眼输出能够保持 CUDA 资源形式。

任一条件不满足时，应阻止本次运行，并将具体原因显示在 GUI 日志或错误提示中；不得静默关闭功能后继续运行。

### 9.2 自动性能检测与安全上限

能力探测只能确认 NvFRUC 能否运行，不能代表当前 GPU 能够在实际工作负载下稳定达到用户选择的帧率。首次启用 NvFRUC 或校准指纹变化时，必须在当前真实配置下执行一次完整链路性能检测。

检测使用当前实际配置，包括：

- GPU、驱动版本及 NvFRUC 版本。
- 深度模型、推理后端和计算精度。
- 输入分辨率、单眼输出分辨率和立体打包格式。
- 运行模式、合成后端以及网络模式使用的编码器。
- 输出显示器刷新率或网络输出帧率上限。

检测流程：

1. 完成模型、CUDA、NvFRUC 和当前输出后端初始化。
2. 使用实际左右眼尺寸预热完整链路 3 秒，预热数据不计入结果。
3. 在不超过显示器刷新率或编码器上限的条件下，以高目标运行完整的捕获、推理、双眼 NvFRUC、合成和提交链路 10 秒。
4. 统计基础真实帧间隔、双眼 NvFRUC 耗时、最终提交帧间隔、队列积压和完整帧组丢弃率，并使用第 95 百分位帧时间计算可持续上限。
5. 取完整链路各阶段上限的最小值作为实测最高输出帧率，再乘以 0.80，向下取整得到安全上限。
6. 使用安全上限继续验证 5 秒；最终提交帧率达到目标的 97% 以上、完整帧组丢弃率不超过 1% 且队列没有持续增长时，校准才算通过。
7. 验证不通过时按 10% 逐级降低候选值并重新验证，直到满足稳定条件或判定当前配置不适合启用 NvFRUC。

校准结果应显示并记录：

- 实测最高输出 FPS。
- 预留 20% 余量后的安全输出 FPS。
- 对应基础推理 FPS。
- 主要瓶颈阶段。
- 校准持续时间和失效原因。

用户设置高于安全上限时，将本次运行的有效目标限制到安全上限，同时更新 GUI 中的目标帧率显示并给出提示；不得继续按不稳定的请求值运行。

校准结果缓存在可写缓存目录，不写入硬件无关的默认配置。缓存键至少包含 GPU UUID、驱动版本、NvFRUC 版本、模型、推理后端、精度、输入及输出尺寸、输出格式、运行模式、合成后端和编码器。任一字段变化都必须重新检测，不能跨设备或跨分辨率复用。

运行期间继续监测最终提交帧率、帧组丢弃率和队列深度。连续三个 3 秒窗口无法达到有效目标的 95%，或帧组丢弃率持续超过 2% 时，将有效目标降低 10% 并记录降档原因；运行中只允许自动降低，不自动升高，避免反复波动。

### 9.3 运行中恢复

运行期间发生单次 NvFRUC 错误时：

1. 记录错误码、分辨率、CUDA 设备和源帧组编号。
2. 注销当前资源并重置左右眼历史。
3. 临时直通真实帧，确保画面不会黑屏。
4. 等待输入分辨率和格式稳定。
5. 自动尝试一次重新初始化。
6. 再次失败后保持真实帧直通，并持续显示明确警告，不循环高频重试。

以下变化必须触发资源重建：

- 左右眼分辨率变化。
- Half-SBS、Full-SBS、TAB 等输出格式变化。
- CUDA 设备或上下文变化。
- 输入像素格式变化。
- 运行模式重新启动。

## 10. 旧逻辑清理

- 删除高级网络推流对 `Lossless Scaling Support` 的专有限制。
- 删除查找 `Stereo Viewer` HWND、捕获窗口所在显示器区域及相关裁剪计算。
- 不再启动或要求外部 Lossless Scaling。
- 删除旧 LSFG 状态、提示文字和无调用的特殊参数传递。
- 如旧 RTMP 窗口捕获模块仍有其他兼容用途，只移除其中的 Lossless Scaling 分支，不扩大本次清理范围。

## 11. 日志与可观测性

启用帧生成后，每个统计周期至少记录：

- 基础捕获 FPS。
- 基础推理/真实立体帧 FPS。
- NvFRUC 生成帧 FPS。
- 最终提交 FPS。
- 左右眼 NvFRUC 平均处理耗时。
- 最终呈现队列深度。
- 完整帧组丢弃数量。
- NvFRUC 重置和回退次数。
- 实测最高 FPS、安全上限、当前有效目标和自动降档次数。
- 校准或运行时识别出的主要瓶颈阶段。

建议日志格式：

```text
[NvFRUC] base=30.0 generated=30.0 submitted=59.8 target=60
left_ms=1.2 right_ms=1.2 queue=1 group_drop=0 resets=0
```

不得只把生成帧计入原有 SBS FPS，以免用户误以为深度推理本身已经达到最终帧率。

## 12. 测试计划

### 12.1 单元测试

- 新旧配置读取优先级和迁移保存。
- 所有运行模式均能解析帧生成开关。
- 30、45、60、90 FPS 的基础帧率换算。
- 真实帧和中间帧的 FIFO 顺序及时间戳。
- 左右眼使用相同源帧组和目标时间戳。
- 最终队列压力下按完整帧组丢弃。
- 停止、异常和分辨率变化时资源完整释放。
- DLL 缺失、不支持 GPU、初始化失败和运行中失败处理。
- 关闭帧生成时保持原有只取最新帧行为。
- 校准指纹生成、缓存命中和配置变化失效。
- 20% 安全余量计算、5 秒稳定性验证和逐级降档。
- 用户目标超过安全上限时的 GUI 更新和有效帧率限制。
- 运行中连续不稳定窗口触发降档且不会自动升档。

### 12.2 模式回归

分别验证：

1. 本地查看。
2. 3D 显示器。
3. OpenXR。
4. MJPEG。
5. 高级网络推流。

每种模式至少检查：

- 未出现额外补帧窗口。
- 左右眼没有交换、不同步或重复。
- 最终分辨率和输出格式正确。
- 停止运行能够及时释放资源。
- 关闭功能后行为与当前版本一致。

### 12.3 格式验证

对以下格式逐项验证：

- Half-SBS。
- Full-SBS。
- TAB。
- 本地显示的保持比例、裁剪铺满和拉伸铺满策略。

重点检查中央接缝、双眼视差、宽高比、生成帧尺寸及 OpenXR 单眼分辨率。

### 12.4 性能与稳定性

- 目标 60 FPS 时，基础推理约为 30 FPS，最终提交接近 60 FPS。
- 在低性能 NVIDIA GPU、不同分辨率及不同模型下验证自动检测结果，确认安全上限始终低于实测极限并保留约 20% 余量。
